# AI Usage Policy

This course does not pretend AI tools don't exist, and it does not treat
them as a shortcut to avoid. Professional developers use documentation,
error messages, search engines, source code, developer forums, and AI
tools — often all in the same hour. This course teaches students to use
all of them, including AI, while making sure their own problem-solving
ability is what actually grows.

The policy below applies in three stages that track the course's overall
reduction in guidance (see `TEACHING_GUIDE.md`).

## Stage 1 — Guided AI use (Weeks 1–4)

- Students may use AI tools to help understand a concept or an error
  message, the same way they'd use documentation.
- Students should be encouraged to first try official documentation,
  read the actual error message, and reason about the problem themselves
  before asking an AI tool.
- AI-suggested code should not be pasted in without the student reading
  and explaining it. Instructors should ask "what does this line do?"
  when a student uses AI-produced code.
- Copying a full solution from AI without understanding it defeats the
  purpose of these weeks and should be corrected immediately when seen.

## Stage 2 — Restricted AI use (Weeks 5–9)

- AI tools may be used for narrow, specific help (e.g. "why does this
  SQL query error," "what does this Django error mean") but not for
  generating whole features or whole files.
- Students should default to official documentation and error messages
  first, treating AI as a second resource, not a first one.
- During project/practical assessments in this stage, AI use is limited
  to the same narrow, specific-question use — not "write this endpoint
  for me."

## Stage 3 — Independent development (Weeks 10–12, including the capstone)

- Students work as independently as possible. AI tools may still be used
  for genuine research questions (e.g. "what does this specific library
  function do," "what does this stack trace mean") but not to generate
  the application's models, views, or business logic on the student's
  behalf.
- The capstone project (Week 12) is explicitly designed to measure what
  the student can build themselves. Instructors should treat capstone
  submissions where the student cannot explain their own code's design
  decisions as a signal to investigate, regardless of whether the code
  works.

## General rules, all stages

- A student should always be able to explain, in their own words, any
  code in their project — AI-assisted or not. This is checked throughout
  via the practical assessment method in `ASSESSMENT.md`, not by asking
  students to disclose AI use directly (which is easy to answer
  dishonestly and hard to verify).
- AI tools are good at answering "why is this broken" and "what does this
  mean" — encourage that use. They are not a substitute for a student
  learning to read a traceback themselves, which remains a taught skill
  (Week 2 onward, formalized in Week 10).
- Instructors should model good AI use themselves during demonstrations
  when it's genuinely the fastest way to check something (e.g. looking up
  an unfamiliar library function), rather than avoiding it awkwardly.
